### S-001 · Medium · Unlimited free trials by deleting/recreating or multiplying organizations
- **Status:** Closed (verified fixed 2026-10-18)
- **Location:** supabase/migrations/20261101000000_subscription_billing.sql:60-78 (trial trigger), public.create_organization (20261004000000_initial_schema.sql:251), src/app/onboarding/actions.ts:36, src/app/o/[org]/actions.ts `deleteOrg` (ctxRead, stays allowed when expired)
- **Standard:** OWASP A04:2021 Insecure Design (business-logic abuse)
- **Description:** Every new `organizations` row gets a fresh 14-day trial. Nothing links the trial to a person, email, domain, card or Stripe customer, and there is no cap on organizations per user. `deleteOrg` is deliberately allowed with no plan, and it cascades the subscription row away.
- **Exploit scenario:** A user lets team A expire, creates team B (new slug) and gets 14 more days, repeating indefinitely (or just keeps many trial teams). Scripted sign-ups with disposable emails do the same. Cost to the operator: trial teams still send email/SMS through the platform's Resend/Twilio accounts (see S-010) and use database/storage. Existing paying customers are not affected. It is also worth noting the migration itself grants every existing business a new 14-day trial (decided by the user, not a defect).
- **Recommended fix:** (1) Cap organizations per user (e.g. max 3 owned, enforced in `create_organization`). (2) Record a durable trial-used marker keyed on owner user id and on a normalized owner email (or Stripe customer) that survives org deletion; a user who already consumed a trial gets `trial_ends_at = now()` (or a short 1-2 day trial) on later orgs. (3) Require verified email before org creation and add rate limiting on sign-up and `create_organization`. (4) Cap SMS/email volume per trial org.
- **Developer notes:** Fixed (user decision 2026-10-18): trial_claims table (normalised verified email, no foreign keys, never deleted); first team per person gets the trial, later teams start expired with a message to subscribe; unverified email = no trial and nothing recorded; max 3 owned teams enforced in create_organization (advisory-locked against races) and in the onboarding UI. PGlite tests cover delete-and-recreate, plus-tags, gmail dots, unverified, cap.
- **Verification notes:** Re-verified 2026-10-18. CLOSED (logic verified; residual items in S-012/S-013). Evidence: trial_claims has no FK and all API grants revoked (migration:70-77; authenticated gets "permission denied for table trial_claims", probe P2c); verified-email gate and claim-or-expire logic (migration:116-152); claim insert uses ON CONFLICT DO NOTHING on the primary key, so two concurrent creations with the same key serialise on the unique index and only one sees row_count = 1 (a rolled-back creation rolls the claim back too); cap of 3 enforced under a per-user advisory lock (migration:173-177) and mirrored in src/app/onboarding/actions.ts:41-42; direct inserts into organizations/memberships are refused by RLS (probes P2, P2b); delete-and-recreate gives no trial (PGlite suite 96/96, re-run by me). Aliases: "John.Doe+x@Gmail.com", "j.o.h.n.d.o.e@googlemail.com" and "johndoe@gmail.com" all map to johndoe@gmail.com (probe). Fullwidth/IDN spellings do not collapse, but they are different mailboxes, so no bypass. Not verified: real concurrency (PGlite is single-connection), Supabase "Confirm email" setting (see S-013).

### S-002 · Medium · "Read-only when expired" is bypassed by SECURITY DEFINER RPCs and uncovered tables
- **Status:** Closed (verified fixed 2026-10-18)
- **Location:** supabase/migrations/20261101000000_subscription_billing.sql:181-200 (restrictive policies); RPCs `public.set_day_shifts`, `copy_shifts`, `fill_shifts_from_weekly` (20261006000000_schedule.sql:131-136), `move_class_booking`, `move_class_session` (20261029000000_class_changes.sql:131,195,234-235) and `add_team_member`
- **Standard:** OWASP A01:2021 / A04:2021; requirement F6 ("dashboard cannot create or edit anything")
- **Description:** Restrictive RLS only applies to direct table access by the `authenticated` role. SECURITY DEFINER functions run as the table owner and skip RLS, so any staff member of an expired org can still call these RPCs through PostgREST and change shifts and move people or whole sessions. The restrictive policy list also omits `memberships` (update/delete, role changes), `service_staff`, `member_locations`, `workflow_steps`, `workflow_services`, `calendar_connections`, `push_subscriptions`, `profiles`. The app layer (`ctxFor`) blocks the server actions, but the database claim in the migration header ("the dashboard cannot create or change anything") is not true for these paths.
- **Risk:** Limited, because the three things that matter commercially ARE covered by triggers that also fire inside definer functions and for the service role: inserts into `bookings`, `class_sessions`, `class_waitlist`, and the location/staff limits. No cross-tenant exposure. The residual risk is a lapsed customer continuing to manage scheduling data without paying, and a gap between the documented and actual behavior.
- **Recommended fix:** Add `private.billing_entitled(org_id)` checks inside the authenticated-callable definer RPCs that write (shifts, move_class_*), and add restrictive policies (or triggers) for the omitted child tables. Add a DB test that, as an authenticated owner of an expired org, every RPC granted to `authenticated` fails. Alternatively soften the documentation: state exactly what stays editable.
- **Developer notes:** Fixed with D-001 and D-002 (definer RPCs check the plan; missing tables covered).
- **Verification notes:** Re-verified 2026-10-18. CLOSED. Evidence: restrictive insert/update/delete policies on 16 org tables (migration:357-371), memberships update/delete with a self-leave exception (374-377), service_staff/member_locations/workflow_services via parent lookup (383-396), organizations update (399-400); move_class_booking/move_class_session check billing_entitled after the permission check (552-554, 619-621); set_day_shifts, copy_shifts, fill_shifts_from_weekly are SECURITY INVOKER (20261006000000_schedule.sql:55-62, 20261019000000_schedule_locations.sql:20,63), so RLS applies. My probes as an authenticated owner of an expired org: set_day_shifts (existing and new day), fill_shifts_from_weekly, copy_shifts all fail with the restrictive-policy error and the existing shift is unchanged; add_team_member and accept_invitation (pending invite created before expiry) fail with the billing message; move_class_* refused (suite). A policy-coverage query over every public table shows the only tables with an authenticated write path and no restrictive policy are profiles and push_subscriptions (own-row only, not organisation data); delete of the whole organisation stays allowed and cascades (probe P6). A member can still leave (probe P7) and reads/exports are untouched (src/app/api/export/[kind]/route.ts has no plan gate).

### S-003 · Medium · Billing webhook trusts the event payload and does not reject Connect events
- **Status:** Closed (verified fixed 2026-10-18)
- **Location:** src/app/api/stripe/billing-webhook/route.ts:54-86; src/lib/billing-server.ts:239-260 (`applyStripeSubscription`, metadata hint)
- **Standard:** OWASP A08:2021 Software and Data Integrity Failures
- **Description:** Signature verification itself is correct (raw `request.text()`, own secret `STRIPE_BILLING_WEBHOOK_SECRET`, default 300 s tolerance, generic 400, 501 when unconfigured). But after verification the handler (a) never checks `event.account`, so if the endpoint is ever created in Stripe as a Connect ("Connected and v2 accounts") listener, subscription events from any tenant's own Stripe account would be processed, and (b) for `customer.subscription.*` it applies the embedded object instead of re-fetching it from Stripe. `applyStripeSubscription` falls back to `metadata.org_id` and accepts it when the org has no stored customer yet. A tenant who controls their own connected Stripe account can set that metadata and an `active` status. Plan items map by price id, so extras cannot be forged without our price ids, but a free `active` base plan can.
- **Exploit scenario:** Operator follows docs step 3 and, while a Connect endpoint already exists, picks "Connected accounts" for the new endpoint. A tenant creates a subscription with `metadata.org_id=<own org id>` in their own Stripe account; the event arrives with `account=acct_...`, matches the org that has no stored customer, and the org becomes `active` with no payment. Requires misconfiguration, hence Medium rather than High.
- **Recommended fix:** Reject `event.account` set; check `event.livemode` against the key mode; re-fetch the subscription via `stripe.subscriptions.retrieve(sub.id)` with the platform key (also fixes ordering, S-008) and do not use `metadata.org_id` as a binding unless the subscription was fetched from the platform account; add to docs/billing-setup.md that the endpoint must listen to "Your account" events only.
- **Developer notes:** Fixed: webhook ignores events with event.account set and events from the other mode; every subscription.*/invoice/checkout event re-reads the subscription from Stripe with our own key; docs/billing-setup.md says to create the endpoint for "Your account" events, not Connect.
- **Verification notes:** Re-verified 2026-10-18. CLOSED. Evidence: signature on raw body with own secret (route.ts:26-33); event.account set is acknowledged and ignored (36); livemode compared with the key mode (38-39); every subscription/invoice/checkout event re-reads the subscription from Stripe with our key (73-76, 84-105); metadata/client_reference_id is only a hint, accepted only if the org has no customer yet or the same customer (billing-server.ts:334-338), and the subscription it is applied to now always comes from our own Stripe account; docs/billing-setup.md:15 says "Your account" events. Webhook suite 26/26 re-run by me. Residual (Info): if the operator ever creates a Stripe Payment Link for the same prices, the payer controls client_reference_id and could attach a paid subscription to an org that has no customer yet (a gift, not a privilege escalation). Do not create Payment Links for these prices.

### S-004 · Medium · Concurrent Checkouts produce duplicate paid subscriptions
- **Status:** Closed (verified fixed 2026-10-18)
- **Location:** src/app/o/[org]/settings/billing/actions.ts:32-45; src/lib/billing-server.ts:115-134, 263
- **Standard:** OWASP A04:2021 Insecure Design (financial integrity)
- **Description:** `startCheckout` only checks the local row (`hasLiveSubscription`). Two tabs (or a double submit) each create a Checkout Session for the same customer; the owner can pay both. The second subscription is then ignored locally (`applyStripeSubscription` returns null at line 263 because a different live subscription exists) but Stripe keeps billing it. Nothing alerts anyone.
- **Risk:** Customer is double charged with no in-app way to see or stop it; refund/dispute burden for the operator.
- **Recommended fix:** Before creating a Checkout Session list the customer's subscriptions in Stripe and refuse if one is active/past_due; give the Checkout Session an `expires_at`; in the webhook, when a second live subscription arrives for an org that already has one, cancel it immediately and refund/log it (and alert the operator).
- **Developer notes:** Fixed with D-004.
- **Verification notes:** Re-verified 2026-10-18. CLOSED (residual S-016). Evidence: createCheckoutUrl asks Stripe for a live subscription on the customer before creating a session (billing-server.ts:150-166); session expires_at and an idempotency key per org/plan/10-minute bucket (171-188; expires_at is bucket start + 3600 s, always at least 50 minutes ahead, inside Stripe's 30 min-24 h window); a second live subscription for an org that already has one is cancelled only after Stripe confirms ours is still live (342-359); startCheckout also refuses when the local row is live (actions.ts:52). Two different plans in two tabs can still both be paid; the loser is cancelled, but the charge is not refunded automatically (S-016).

### S-006 · Low · Cron secret comparison not timing-safe
- **Status:** Closed (verified fixed 2026-10-18)
- **Location:** src/app/api/cron/reminders/route.ts:15
- **Standard:** OWASP A07:2021
- **Description:** `authorization !== \`Bearer ${env.cronSecret}\``. It does fail closed when `CRON_SECRET` is unset (401), which is good, and the route is excluded from the proxy matcher. The compare is not constant-time; network-level timing attacks are impractical, hence Low. The billing sweep it triggers is idempotent, so an unauthenticated call would not do harm anyway.
- **Recommended fix:** `crypto.timingSafeEqual` on equal-length buffers (hash both first); enforce a minimum secret length.
- **Developer notes:** Fixed: src/lib/secure-compare.ts (sha256 both sides then timingSafeEqual); the cron route fails closed when CRON_SECRET is unset. Unit tested.
- **Verification notes:** Re-verified 2026-10-18. CLOSED. Evidence: src/lib/secure-compare.ts:7-17 (SHA-256 of both sides, timingSafeEqual, false when secret or header is missing); used at src/app/api/cron/reminders/route.ts:17. Hardening suggestion (not a defect): enforce a minimum CRON_SECRET length at startup.

### S-008 · Low · Idempotency and ordering gaps
- **Status:** Closed (verified fixed 2026-10-18)
- **Location:** src/app/api/stripe/billing-webhook/route.ts:32-48; src/lib/billing-server.ts:156, 194, 213 (direct applies), 265, 303, 321, 328-338
- **Standard:** OWASP A04:2021
- **Description:** (1) A duplicate that arrives while the first delivery is still processing (row exists, `processed_at` null) is processed concurrently, so "started" emails can be sent twice. (2) Ordering uses `event.created` in whole seconds with a strict `>` comparison, so two events in the same second can apply out of order. (3) Direct applies after Checkout confirmation, plan change and cancel do not stamp `last_stripe_event_at`, so a stale snapshot can briefly overwrite a newer local state until the next event. (4) `invoice.payment_failed/paid` without a subscription id fall back to matching by customer, so a one-off invoice on the customer could start the 7-day grace period. (5) `stripe_billing_events` rows are never purged.
- **Recommended fix:** Re-fetch the object from Stripe in the handler (fixes 2 and 3); claim the event with an atomic `processing` state (or advisory lock) and retry staleness window; require a subscription id on invoice events; add a retention job (e.g. 90 days).
- **Developer notes:** Fixed: insert-first event claim with 409 for in-flight duplicates; compare-and-set update; direct applies stamp last_stripe_event_at; events are applied from a fresh Stripe read so same-second events are harmless; invoice events need a subscription id (no customer fallback); owner email only when a problem starts; events older than 90 days are purged by the sweep.
- **Verification notes:** Re-verified 2026-10-18. CLOSED. Evidence: (1) insert-first claim, 23505 -> processed? ack : in-flight? 409 : compare-and-set takeover after 5 minutes (route.ts:43-56), failure releases the claim (58-66); (2) subscription always re-read from Stripe (route.ts:73-76) and the update is compare-and-set on status (billing-server.ts:386); (3) direct applies stamp last_stripe_event_at (164, 212, 253, 272); (4) invoice events require a subscription id (route.ts:102-112); (5) 90-day purge in the sweep (559-561). Covered by the 26 webhook tests I re-ran (replay, out-of-order, in-flight 409, retry after 500, purge). Minor: a locally stamped nowSeconds() can be ahead of Stripe's clock and make a genuinely newer Stripe event look stale (billing-server.ts:362); the next hourly sweep repairs it.

- **Verification notes:** Re-verified 2026-10-18. CLOSED. Evidence: missing subscription row = not entitled (migration:212); EXECUTE revoked from PUBLIC/anon/authenticated on every private trigger/helper function (512-528, probe P1: authenticated calling private.email_key gets "permission denied for function"); org_accepts_bookings stays anon-callable and returns false for an unknown id and for an expired org alike (probe P9; it only tells "can take bookings", the slug is already public); billing_status is not granted to anon and strips dates/past_due for non-owners (482-509; suite).

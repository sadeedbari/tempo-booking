### Failures
1. `e2e/api/billing.test.mjs:254` "failed payment: owner is emailed, 7 days of grace, then expired; paying fixes it". Expected status `expired` after the hourly job, got `past_due`. Reproduced on a second isolated run. Category (a) billing-feature defect (Medium).
   Probable cause (code + diagnostic run): in `runBillingSweep` (src/lib/billing-server.ts ~l.628) the past-due-beyond-grace row is set to `expired`, then in the same sweep `reconcileWithStripe` (l.680-712) re-reads Stripe, which still says `past_due` (Stripe keeps retrying), and `applyStripeSubscription` writes it back to `past_due`, counting expired -> past_due as "started". Diagnostic: after 2 cron runs the status is `past_due` and the owner received 2 emails "Your Tempo subscription is active" (the "started" mail). So in production, a business whose card keeps failing past 7 days would flip each hour and receive an hourly, misleading "subscription is active" email. Entitlement stays false (billing_entitled uses past_due_since + 7 days), so access control is still correct; the defect is the status flip-flop and the email spam. Fix idea for developer: reconcile must not turn `expired` into a paying status from a Stripe `past_due`, and/or "started" must exclude the expired -> past_due transition; keep `expired` sticky until Stripe says active.
2. `10-monkey.spec.ts` "monkey: adminA > schedule": test timeout 280 s (stuck in the dialog loop). Passed in 17.6 s when re-run alone. Category (b) flaky harness/environment, not the billing feature (the page set does not depend on billing; ownerA and staffA1 passed the same pages, including settings/billing for owner). Not reproduced; unexplained stall (a slow page.goto or a dialog that never closed is likely).
